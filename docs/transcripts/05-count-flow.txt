  Feature 05 plan: mobile count flow

  Scope

  Included:
  - Search for a bin: type or scan its code (a hardware scanner that types the
    code works too).
  - Count sheet: shows the expected pallets and their product lines.
  - Counting: enter a counted quantity for each line and see the auto pass/fail
    update as you type.
  - Save: override the result if needed, then save. One API transaction then
    does all five steps: lock the bin and set lastAuditedAt, store the result,
    create adjustments if the final result is FAIL, mark the task DONE, and
    recompute the score with the AUDIT trigger.
  - Result screen: shows the score before and after the count, and links to the
    next pending task.

  Left out:
  - Scanning with the phone camera
  - Recording products found on the shelf that the system doesn't expect
  - Editing or deleting audit results
  - Offline mode
  - Counting more than one bin at a time

  Changes

  Shared: a new packages/shared/src/count.ts with the types below:
  - CountSheetResponse: binId, code, pendingTask, toleranceUnits, and the
    pallets, each with lines { palletItemId, sku, name, expectedQty }
  - SubmitCountRequest: { lines: [{ palletItemId, expectedQty, countedQty }], 
    finalOutcome }
  - CountResultResponse: auto and final outcome, totals, discrepancy ratio, each
    line with its difference, the number of adjustments, previousScore →
    newScore, and the task it completed

  API (apps/api/src/audits/):
  - count.config.ts: holds toleranceUnits: 0, the single source of truth for the
    tolerance (D-002)
  - count.evaluation.ts: a pure function that takes the lines and the tolerance
    and returns each line's difference, the auto outcome, the totals, and the
    discrepancy ratio (0 when nothing is expected)
  - count.validation.ts: a pure check that the submitted lines match the bin's
    current lines exactly
  - audits.service.ts, audits.controller.ts, audits.mapper.ts, audits.module.ts
  - Endpoints:
    - GET /bins/:code/count-sheet returns CountSheetResponse. It uses the bin
      code, as D-062 says, and is case-insensitive like the bin detail endpoint.
    - POST /bins/:code/counts takes SubmitCountRequest and returns 201 with a
      CountResultResponse.
      - It returns 400 for an invalid body (counts must be whole numbers ≥ 0)
        and 404 for an unknown bin.
      - It returns 409 when the inventory changed since the sheet was loaded:
        lines were added or removed, or an expectedQty is different.
  - Transaction order (CLAUDE.md "On save", D-056, D-057):
    a. UPDATE "Bin": set lastAuditedAt = now. This is the first write, so it
       takes the bin lock.
    b. Read the pallet lines again and validate the submission against them (409
       if they don't match).
    c. Create the AuditResult and its lines, linked to the bin's PENDING task if
       it has one.
    d. If the final outcome is FAIL: for each mismatched line, create an
       ADJUSTMENT movement with auditResultId set and the quantity change, then
       set the line's quantity to the counted value.
    e. Mark the task DONE and set completedAt.
    f. Call scoring.recomputeBin(binId, 'AUDIT', auditResultId, tx).
  - No migration. The schema already covers all of this.

  Web:
  - /count: a large code input (autoCapitalize, autofocused, submits on Enter)
    that goes to /count/[binCode], and a list of pending tasks to tap, in rank
    order.
  - /count/[binCode]:
    - The page loads the count sheet on the server. A client form shows one card
      per pallet, with a numeric input (inputMode="numeric") for each line.
    - A sticky footer shows the live auto pass/fail, an override toggle, and the
      Save button.
    - Saving runs a server action. On 409, the page shows "Inventory changed,
      reload the sheet".
    - A result panel shows the outcome, the discrepancy, the score before and
      after, and "Next pending task".
  - Links: a "Count" link in the nav, and "Count this bin" links in the bin
    drawer and the tasks table.

  Business rules applied

  - Pass/fail is an exact match by default, with configurable tolerance. The app
    stores both the auto and the final outcome (D-002).
  - Counts are entered per pallet line (D-003).
  - If the final outcome is FAIL, the app creates audit-generated adjustments
    and corrects inventory. If it is PASS, it records the differences only
    (D-004).
  - The recompute after a count covers only the audited bin (D-005).
  - The bin row is the first write, so the count and a concurrent recompute
    can't overwrite each other (D-056, D-057).
  - The count sheet skips lines with quantity 0, like D-055 and D-065 (see
    question 1).

  Tests

  - Unit:
    - evaluateCount: all lines match, one line off, tolerance > 0, an empty bin,
      ratio math
    - Submission validation: a missing, extra, duplicate, or stale line
    - The controller's body validation
    - The mapper
  - E2e (apps/api/test/count-flow.e2e-spec.ts, against the seeded database):
    - A PASS count completes the task, adds an AUDIT score linked to the result,
      and resets factors 1–3.
    - A FAIL count creates adjustments with auditResultId and updates the
      quantities.
    - An override from FAIL to PASS creates no adjustments.
    - An ad-hoc count (no task) works.
    - A stale sheet returns 409; an unknown bin returns 404; an invalid body
      returns 400.
    - Every test restores the seeded data afterwards (the same cleanup approach
      as the scoring race test).

  Open questions (my recommendation first)

  1. Lines with quantity 0: leave them off the count sheet, as the drawer does,
     or show them so the counter can report stock that turned up? I recommend 
     leaving them off.
  2. Scanning: text input only, which works with hardware scanners, or also
     camera scanning with BarcodeDetector? Safari doesn't support
     BarcodeDetector. I recommend text input only.
  3. Stale sheet: reject with 409 and make the counter reload, or save against
     the current quantities? I recommend 409, so the auto outcome the counter
     saw is the one that gets saved.
  4. Empty bin (no lines): allow a count that passes automatically, or refuse
     it? I recommend allowing it, because it confirms the bin really is empty.
