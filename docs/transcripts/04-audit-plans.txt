  Feature 04 plan: audit plans and tasks

  Scope

  In scope
  - Generate a plan: you enter N and the API creates a plan from the top N bins
    by current score, skipping bins that already have a PENDING task (D-006).
    Existing tasks are never touched.
  - List plans and tasks: a tasks table showing bin, rank, score when the task
    was created, current score, status, plan, and dates. It can be filtered by
    status.
  - /tasks page: the N input, a "Generate audit plan" button, and the tasks
    table. A top nav links Heatmap and Tasks.
  - Pending-task badges: these were deferred from feature 03 (D-060). A heatmap
    cell gets a marker when its bin has a PENDING task, and the bin drawer shows
    "Pending audit task · plan #X, rank Y".

  Out of scope: completing tasks or counting (feature 05; tasks only become DONE
  there), cancelling or deleting tasks and plans, pagination, live updates, and
  recomputing scores before planning.

  How plan creation works, in one transaction:
  1. Take pg_advisory_xact_lock, so two plans created at the same time can't
     pick the same bins.
  2. Load the eligible bins: no PENDING task and a current score.
  3. selectTopBins(candidates, n) picks them: score descending, ties broken by
     bin code.
  4. Insert the plan and its tasks with createMany({ skipDuplicates: true }).
     Postgres's ON CONFLICT DO NOTHING also covers the partial index, so a
     violation counts as "already pending" and gets skipped, as CLAUDE.md
     requires.
  5. Store scoreAtCreation as a snapshot. Ranks run 1..k.

  The warehouse and bins services also select each bin's pending task so the
  badges can use it.

  Web
  - app/tasks/page.tsx: a server component that reads ?status=.
  - app/tasks/actions.ts: a generateAuditPlan server action using
    useActionState, like RecomputeButton. It calls refresh() afterwards.
  - components/audit-plans/: PlanForm, TasksTable, StatusFilter. Bin codes link
    to /?bin=CODE.
  - layout.tsx: the nav header. RackGrid and BinDrawer show the pending badge.

  Business rules

  - Top N by current score, skipping bins with a PENDING task. The next riskiest
    bins fill the free slots (D-006).
  - Existing PENDING tasks are never modified, and there is at most one per bin
    (the DB index plus skip-on-conflict).
  - If fewer bins are eligible than N, the plan gets the bins that are left.
    requestedN keeps the N you asked for, and the UI says "Created plan #4 with
    3 of 5 requested tasks".
  - Bins with no score are not eligible.

  Tests

  - Unit: selectTopBins (ordering, tie-break, N larger than the candidate list,
    empty list); plan-size validation in the controller spec (0, 101, 2.5,
    "abc", missing); mappers (task row, plan summary); the warehouse and bins
    mappers with pendingTask.
  - E2E (test/audit-plans.e2e-spec.ts, seeded DB, cleans up its plans and
    tasks):
    - N=3 creates ranks 1–3 in score order that match the top eligible bins.
    - A second N=3 plan skips those bins.
    - N larger than the eligible count creates only the remaining bins.
    - Invalid N returns 400.
    - The GET /audit-tasks filters work.
    - Two concurrent POSTs never produce duplicate pending bins.
    - The layout and bin detail show pendingTask.

  Open questions

  1. No eligible bins (every scored bin already has a pending task): I recommend
     returning 409 Conflict without creating a plan, so the list never fills
     with empty plans. The alternative is to create an empty plan.
  2. Upper limit for N: I recommend 1–100, a general cap rather than the current

  3. Pending badges in this feature: I recommend yes, since D-060 deferred them
