  Business rules and how each is implemented

  - Window: movements with occurredAt > lastAuditedAt count toward the score. A
    never-audited bin uses its full history.
  - Factor 1: (now − lastAuditedAt) in days. A never-audited bin gets the
    threshold (30), which normalizes to 1.
  - Factor 2: PICK + PUTAWAY + MOVE, counting a move whether the bin is binId or
    fromBinId (D-012).
  - Factor 3: ADJUSTMENT movements with auditResultId IS NULL only.
  - Factor 4: audits with finalOutcome = FAIL and countedAt ≥ now − 90d. Not
    reset by an audit (D-013).
  - Factor 5: discrepancyRatio of the latest AuditResult, ignoring any override.
    A never-audited bin gets 0.
  - Factor 6: min((skus − 1) / 5, 1). An empty bin gets 0.
  - Score: round(Σ normalized × weight × 100). Each history row stores the
    threshold and weight it used (D-014). Rows are append-only.

⏺ The review found one finding (medium).

  apps/api/src/scoring/scoring.service.ts:16: a concurrent manual recompute can 
  overwrite a fresh AUDIT score.

  Here's the race:
  1. recomputeAll reads the inputs for all bins. Under Postgres's default
     isolation level, it sees each bin as it was before any count still in
     progress.
  2. While it runs, the count flow saves an audit for bin X and commits its
     AUDIT score.
  3. recomputeAll then reaches bin X and points currentScoreId at a
     MANUAL_RECOMPUTE row built from the inputs it read before the count.

  The heatmap and the next audit plan would then rank that bin as if it had
  never been counted. Nothing triggers this yet, because the count flow is
  feature 05. But recomputeBin(…, tx) exists for that flow, so it's best to
  settle the locking now.

  Proposed fix: lock the bins' rows, in id order, before reading any inputs.
  Under the default isolation level, every query after the lock sees the latest
  committed data. A recompute then either waits for an in-progress count to
  finish and scores the counted state, or makes that count wait until it's done.
  Locking in id order means two full recomputes can't deadlock each other.
