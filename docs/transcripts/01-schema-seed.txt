  - Cambios al schema: el modelo ya está en la migración init.

  Diseño: simulación hacia adelante

  Para que los datos sean consistentes por construcción, el seed no inventa un
  estado final y sus movimientos por separado. Simula los 30 días en orden
  cronológico con un PRNG con semilla fija (mulberry32):
  - Día −30: PUTAWAY inicial de los pallets.
  - Cada día, por bin: según su perfil de riesgo (cold / warm / hot) ocurren
    picks (que nunca dejan una cantidad negativa), putaways de pallets nuevos,
    moves entre bins y ajustes manuales.
  - Auditorías históricas en algunos bins: toman una foto de la cantidad
    esperada, el conteo es la cantidad esperada más ruido según el perfil y se
    aplican las reglas de D-004. Si el resultado es FAIL, se crean ADJUSTMENT
    con auditResultId y se corrige la cantidad. Además se actualiza
    lastAuditedAt.

  Las fechas son relativas a "ahora", así que el seed siempre cubre los últimos
  30 días. Con la misma semilla, los datos salen iguales en cada ejecución.

  Plan: Feature 01: Seed data (01-schema-seed)

  Scope

  In scope:
  - A deterministic seed that creates:
    - One warehouse with 36 bins: 3 aisles (A–C) × 2 racks × 2 levels × 3

  Out of scope:
  - Computing scores. The SEED BinScore rows need the calculator, which is
    feature 02. In 01, currentScoreId stays null. Feature 02 adds the "compute
    SEED scores" step to the seed.
  - Audit plans and tasks. The seed creates no AuditPlan/AuditTask rows, so past
    audits are ad-hoc (taskId = null).
  - Schema changes. The model is already in the init migration.

  Design: a forward simulation

  The seed doesn't invent a final state and its movements separately, which
  could contradict each other. Instead it runs the 30 days in order with a
  fixed-seed random number generator (mulberry32), so the data is consistent by
  construction:
  - Day −30: pallets are put away (PUTAWAY).
  - Each day, per bin: what happens depends on the bin's risk profile (cold /
    warm / hot): picks (never below 0), putaways of new pallets, moves between
    bins, and manual adjustments.
  - Past audits on some bins: the audit snapshots the expected quantities. The
    counted quantity is the expected one plus noise based on the profile. D-004
    then applies: on FAIL, ADJUSTMENT movements are created with auditResultId
    and the quantities are corrected. lastAuditedAt is updated either way.

  Dates are relative to "now", so the seed always covers the last 30 days. The
  same seed always produces the same data.

  Target profile mix, to get the green/yellow/red spread CLAUDE.md asks for:

  ┌────────┬──────────────────────────────────────────────────┬─────────────┐
  │ Color  │                       Bins                       │  Expected   │
  │        │                                                  │    score    │
  ├────────┼──────────────────────────────────────────────────┼─────────────┤
  │ Green  │ Recent passed audit, low activity                │ ~5–20       │
  ├────────┼──────────────────────────────────────────────────┼─────────────┤
  │ Yellow │ Never audited or audited long ago, medium        │ ~30–55      │
  │        │ activity                                         │             │
  ├────────┼──────────────────────────────────────────────────┼─────────────┤
  │ Red    │ High activity, manual adjustments, and 1–2       │ ~65–90      │
  │        │ failed audits with large discrepancies           │             │
  └────────┴──────────────────────────────────────────────────┴─────────────┘

  A never-audited bin starts at 25 points from factor 1 alone, so the green bins
  depend on recent passed audits. The exact scores get checked in 02, once the
  calculator exists.
